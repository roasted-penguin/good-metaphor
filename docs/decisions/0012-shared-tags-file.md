# 0012 추상 태그는 공통 파일 tags.json, 합치는 곳은 런타임마다 로더 한 곳

- 상태: 결정 (2026-11-08, T-304)

## 배경
추상 태그 18개(통제 어휘, 규칙 9)가 관심사 그래프 `extension/data/common/maplestory.json` 안에 있었다. 두 번째 관심사 식당(T-302)과 커스텀 관심사(T-301)도 같은 태그를 써야 금융 문장과 구조가 같은 노드를 관심사와 상관없이 찾을 수 있다. 서버의 추출 어휘(T-412)와 질의 키워드 프롬프트도 같은 목록에서 나와야 한다. 태그가 메이플 파일에 묶여 있으면 관심사를 늘릴 때마다 복사본이 생기고 어긋난다.

## 결정
- 태그 원본은 `extension/data/common/tags.json`(`{ version, note, tags: [...] }`)이다. 관심사 그래프 파일에는 `tags`가 없고, 노드 `tags`에 태그 id만 적는다.
- **합치는 곳은 런타임마다 로더 한 곳이다.** 로더가 같은 폴더의 `tags.json`을 읽어 `{ ...graph, tags }`로 합친 "해석된 그래프"를 돌려주고, 그 아래(`mergeGraphs`, `retrieve`, `nodeText`, 서버 파이프라인·시드·추출)는 지금처럼 `graph.tags`를 쓴다.
  - 확장: `lib/stores.js` `loadCommonGraph`(병합 규칙은 `lib/graph.js` `resolveCommonGraph`)
  - Node 도구·테스트: `tools/load-graph.mjs` `loadCommonGraphFromDisk`
  - 서버: `app/config.py` `load_common_graph`(`Settings.common_graph()`). 경로는 `TAGS_PATH`, 기본값은 그래프 파일 옆(금칙어와 같은 규칙). 도커는 `/data/common/tags.json`.
- 태그 순서는 파일 순서 그대로다. 순서가 바뀌면 `nodeText`가 바뀌어 벡터 캐시와 검색 순위가 바뀐다. 분리할 때 순서를 그대로 옮겼고 단위 테스트가 순서와 `nodeText` 스냅숏을 고정한다.
- 공통 그래프 검증에서 노드가 태그 파일에 없는 id를 참조하면 **오류**다. 사용자 오버레이의 없는 태그는 지금처럼 `mergeGraphs`가 조용히 버린다.
- 하위 호환: 그래프에 `tags`가 이미 있으면(예전 형식의 원격 공통 저장소) 태그 파일 없이 그대로 쓴다. 원격 그래프에 `tags`가 없으면 같은 주소 폴더의 `tags.json`을 받는다.

## 결과
- 식당·커스텀 관심사가 같은 태그 파일을 참조할 수 있다. 관심사 파일은 노드·엣지만 가진다.
- 검색 결과는 분리 전과 같다(`npm run eval:fallback` 출력 동일, `nodeText` 스냅숏 동일).
- 추출 어휘와 키워드 프롬프트 어휘가 같은 `tags.json`에서 나오는지 서버 테스트가 확인한다(규칙 9).
- 서버 판본(`workspace_version`, 결과 캐시 키)은 `"그래프 판본+태그 판본"`이라 `tags.json`의 `version`만 올려도 캐시가 갈린다(`WORKSPACE_VERSION`이 있으면 그 값, 인라인 tags·태그 파일을 못 읽으면 그래프 판본만). 확장도 `sources.common.tagsVersion`이 결과 캐시 키(`graphKey`)에 들어간다. 태그를 바꾸면 `tags.json` `version`을 올리고, 서버 인덱스는 시드를 다시 넣는다.
- 공통 그래프를 직접 `JSON.parse`/`json.loads`로 읽으면 태그가 빠진다. 새 도구·테스트는 위 로더를 쓴다.
- (T-302, 2026-11-09) 공통 관심사가 둘(메이플·식당)이 됐다. 확장 `loadCommonGraph(interestId)`, Node `loadInterestGraph(interestId)`·`commonGraphPath(interestId)`가 같은 폴더의 `<id>.json` + `tags.json`을 읽는다(목록은 `lib/graph.js` `COMMON_INTERESTS`). 관리자 원격 주소(`commonStore.url`)는 기본 관심사(메이플)에만 쓴다. **서버는 메이플만 안다**(식당은 확장 브라우저 파이프라인만).
- (T-206, 2026-11-23) 22번째 태그 `compliance_procedure`(법정 신고·표시 의무)를 맨 뒤에 더했다. 식당 노드 파이프라인(T-198)에서 법령 조문 후보 27개가 맞는 태그가 없어 버려졌기 때문이다(영업 전 신고·허가·등록, 법정 표시). 예문은 식당·메이플 밖 분야(통신판매업 신고, 화장품 전성분 표시, 택시 자격증명 게시)로 두었다. 실제 확장에서 영어 예문(건축 허가)은 영어 평가 문장을 끌어가고, 의료·인증 분야 예문은 진료 예약·어린이집 문장을 끌어가서 뺐다. 노드는 사실이 이 구조를 직접 말하는 `open_prep`·`price_board`에만 붙였다. `franchise_disclosure`도 구조는 맞지만 붙이면 홀드아웃 1위 회귀가 나서 보류했다. 메이플에는 맞는 노드가 없다. 메이플 병합 그래프는 노드가 쓰는 태그만 남기므로 메이플 일반 검색은 바뀌지 않는다. 정밀 모드 태그 판정 선택지(`tagChoices`)는 병합 그래프의 태그(노드가 쓰는 것만)에서 나온다. 그래서 식당만 17→18개로 바뀌고 메이플 판정 프롬프트는 바이트 단위로 같다(예전 판정 캐시를 그대로 써도 된다). 식당 문장은 새로 물어 확인했다(회귀 0). 앞으로 메이플 노드가 이 태그를 쓰게 되면 메이플 판정 캐시를 다시 물어야 한다.
- (T-219, 2026-11-28) 23~25번째 태그 `queue_rationing`(선착순 배분: 값 대신 줄 서기·먼저 신청한 차례로 나눔)·`self_service`(셀프 서비스: 직원 일을 손님이 맡고 값·시간을 아낌)·`time_window`(허용 시간대 제한: 정한 시간대에만 열리고 밖에서는 금지)를 맨 뒤에 더했다. T-213에서 웨이팅·오픈런·셀프 코너·브레이크 타임 같은 익숙한 식당 장면이 맞는 태그가 없어 버려졌기 때문이다. `time_window`는 `cooldown`(쓴 뒤 기다림)·`periodic_cap`(기간당 횟수)·`temporary_multiplier`(정한 시간에 혜택이 커짐)와 겹치지 않게 "그 시간 밖에서는 아예 못 함"을 구조로 잡았다. 예문은 식당·메이플 밖(운동화 줄 서기·수강신청·주민센터 강좌 / 무인 빨래방·셀프 체크인·조립 가구 / 은행 창구·투표소·공항 야간 운항 금지). **지금은 어느 노드도 쓰지 않는다.** 정직하게 맞는 기존 노드는 `lunch_peak`(queue_rationing)·`business_hours_limit`(time_window)이고, 붙이면 실제 확장 일반 검색은 회귀 0이었다. 그러나 노드가 태그를 쓰면 정밀 판정 선택지가 늘어나는데(식당 18→20), 그러면 판정기가 미용실 홀드아웃 문장을 '법정 표시 의무'로 추상화해 1위가 틀려졌다(다시 물어도 3/3 같음, 선택지 18개면 3/3 맞음). 셀프 서비스는 정직하게 맞는 기존 노드가 없다(`lunch_peak`의 '주문 방식을 바꿔'는 손님이 일을 맡는다고 말하지 않음). 규칙: **이 세 태그를 처음 노드에 붙이는 묶음은 그 관심사의 정밀 판정을 새 선택지로 다시 물어 회귀 0을 확인한다**(일반 관문만으로는 못 잡는다). `time_window` 설명이 법 문구 쪽 추상화를 부추기는지 먼저 확인할 것(T만 붙인 판 1/2). 문구는 한 줄 차이로 결과가 갈렸다(queue 8개 중 1개만 통과). 서버 키워드 프롬프트·추출 어휘는 tags.json 전체를 쓰므로 세 태그가 들어가고, 서버 인덱스는 다시 시드해야 한다(엔티티 = 태그 25 + 노드).

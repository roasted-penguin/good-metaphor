# 0016 커뮤니티·블로그·뉴스 출처를 사실 확인용으로 받는다(메이플·식당)

- 상태: 결정 — 2026-11-23, T-212 (사용자 결정 D-8, 같은 날 식당까지 확대)
- 관련: D-5(문서 출처, 2026-10-11), D-3(검수), T-118(sources·verifiedAt), ADR 0007(최신화), ADR 0015(1,000노드), 규칙 2·3·9·11

## 배경
메이플 공통 그래프를 노드 1,000개까지 늘린다(ADR 0015). 공식 출처(maplestory.nexon.com 가이드 107글 + 패치 노트·공지)만으로는 150~170개 안팎에서 막힌다. 공식 가이드가 다루지 않는 시스템·관행(거래 관습, 성장 경로, 보스 파티 규칙 등)이 많기 때문이다.
D-5(2026-10-11)는 "원문 인덱싱은 공식만, 나무위키·인벤은 참고용(읽고 사실을 확인해 우리 문장으로)"이었고, 노드 출처(`sources`)에는 공식 URL만 남겼다(그래프 테스트가 강제).

## 결정 (D-8, 사용자 2026-11-23)
인벤·나무위키에서 확인한 사실도 노드 출처로 쓴다. 단 아래를 모두 지킨다.
1. **사실만, 우리 문장으로.** 표현(문장·구성·표)은 옮기지 않는다. 저작권은 표현을 보호하고 사실은 보호하지 않는다(저작권법 제2조 1호, 아이디어·사실 비보호 원칙).
2. **원문 저장 금지(D-5 그대로).** 페이지 본문은 검사 동안 메모리에만 있다. 디스크·커밋·서버에는 URL, 우리 문장, 숫자 지표(최장 복사 글자 수, 겹침 비율)만 남는다. LightRAG 서버(T-421)에도 커뮤니티 원문은 인덱싱하지 않는다(원문 인덱싱은 공식만, D-5 결정 그대로).
3. **출처 URL과 출처 종류를 남긴다.** 노드 `sources`에 실제로 열어 확인한 URL, 커뮤니티 URL이 하나라도 있으면 노드에 `sourceKind: "community"`(없으면 생략 = 공식).
4. **교차 확인 필수.** 커뮤니티 출처가 있는 노드는 ① 공식 출처 1개 이상과 함께이거나(공식과 어긋나지 않음 확인), ② 서로 다른 커뮤니티 **사이트** 2곳(나무위키 + 인벤)이 같은 사실을 말해야 한다. 같은 사이트의 두 문서(나무위키 두 쪽)는 독립 출처로 치지 않는다.
5. **충돌 시 공식 우선.** 공식 출처와 커뮤니티 출처가 다르면 공식 문장을 따른다. 커뮤니티에만 있는 사실이 공식과 어긋나면 그 사실은 버린다. 이 판정은 자동으로 못 하므로 리뷰(메인 판정)가 한다.
6. **규칙 2·9·11 그대로.** 자주 바뀌는 수치·패치 번호 금지(커뮤니티 문서는 확률표·가격이 많다), 태그는 통제 어휘만, 멸칭·실존 인물 금지. 커뮤니티 페이지에는 멸칭·실존 인물 언급이 흔하므로 금칙어 검사(`data/common/blocklist.json`)는 생략할 수 없다(파이프라인 check가 항상 돈다).
7. **식당도 같은 규칙(사용자 2026-11-23 확대).** 공공 출처 밖(뉴스, 블로그, 커뮤니티, 표준국어대사전)에서 확인한 사실도 쓴다. 식당 그래프 방향이 법령 조문에서 **누구나 겪어 본 식당 장면**(웨이팅, 점심 피크, 회전율 등)으로 바뀌었기 때문이다(T-213). 추가 규칙: **특정 가게·브랜드 이름 금지**(파이프라인은 커뮤니티 출처 식당 후보에 `storeNameReview` 경고, 영문은 원래 실패), 수치·가격 금지(식당은 숫자 하나도 안 됨, 그대로), 멸칭·실존 인물 금지. 표준국어대사전(`stdict.korean.go.kr`)은 `*.go.kr`이라 공공(official)으로 친다.
8. **독립 출처 단위는 사이트(플랫폼).** 같은 플랫폼의 두 글(티스토리 블로그 둘, 나무위키 두 쪽)은 한 곳으로 친다(보수적 판정: 서로 베꼈을 가능성이 크고, 작성자 독립성을 기계로 가릴 수 없다). 다음 뉴스는 언론사가 달라도 한 곳이다. 공식(공공) 출처 하나는 독립 출처 한 곳이다.

### 자동 가져오기 범위 (판정)
- robots는 정책에 넣은 사이트 모두 문서·게시글 한 쪽 가져오기를 허용한다(robots가 막거나 RAG 금지를 밝힌 사이트는 정책에 넣지 않았다). 그래도 **크롤링(목록·검색·링크 따라가기)은 하지 않는다.** 이유: DB 제작자 권리(제93조, "상당 부분"의 반복·체계적 수집), 나무위키 약관 미확인, 인벤 게시판 목록은 수집 가치보다 위험이 크다.
- 파이프라인이 커뮤니티 페이지를 가져오는 것은 **후보 노드에 이미 적힌 URL 하나를 검사할 때만**(check의 출처 확인: 응답·베낌·겹침). `politeFetcher`가 robots를 지키고(가장 긴 규칙 우선) 호스트마다 1초에 1번 이하, UA에 도구 이름을 밝힌다. robots가 막으면 그 출처는 실패다.
- 커뮤니티 페이지에서 **초안(LLM 추출)은 하지 않는다.** `index`의 목록·씨앗은 공식만이고(`sources.mjs` `allowHost` = 공식 호스트), 커뮤니티 페이지는 색인에 들어가지 않는다.
- 그래서 커뮤니티 사실은 **사람·에이전트가 직접 읽고**(한 쪽씩, URL 기록) 우리 문장으로 후보를 쓴 경우에만 들어온다. 이 후보는 `/add-common-node` 절차나 파이프라인 check(수동 초안 파일)를 거친다.
- robots·약관이 바뀌어 자동 가져오기가 금지되면 check의 출처 확인이 실패하므로 그 출처는 쓸 수 없다. 이때는 이 ADR을 고쳐 "사람 확인 기록"(확인 날짜·확인자) 방식으로 바꿀지 다시 정한다. 그 전까지 가져오지 못한 커뮤니티 출처는 받지 않는다.

## 품질 안전장치 (구현)
- **출처 정책 원본 한 곳:** `tools/source-policy.json`(관심사별 공식·커뮤니티 호스트(`host` 또는 `suffix`)·경로, 커뮤니티는 사이트 id). 메이플 커뮤니티 = `namu.wiki` `/w/`, `www.inven.co.kr` `/board/maple/`·`/maple/`. 식당 커뮤니티 = `namu.wiki` `/w/`, `*.tistory.com`, `brunch.co.kr` `/@`, `v.daum.net` `/v/`. 사이트를 더하려면 위 robots·약관 표에 한 줄을 먼저 쓴다. 판정 함수는 `tools/source-policy.mjs`(`classifySource`·`corroboration`·`checkNodeSources`), 서버 테스트는 같은 JSON을 읽어 같은 판정을 한다.
- **그래프 테스트:** 예전 "메이플 출처는 maplestory.nexon.com만"·"식당은 공공만"은 "모든 노드가 `checkNodeSources` 통과"로 바뀌었다(확장 `tests/unit/graph.test.mjs`·`restaurant.test.mjs`, 서버 `server/tests/test_seed.py`). 허용 밖 주소, 교차 확인 없음(`communityUncorroborated`), 커뮤니티인데 `sourceKind` 없음(`sourceKindMissing`), 공식만인데 `community`(`sourceKindMismatch`)는 실패.
- **`validateGraph`:** `sourceKind`는 없거나 `official`·`community`만. 호스트 판정은 하지 않는다(관심사별 정책은 tools 쪽, 확장 런타임은 출처를 쓰지 않는다).
- **파이프라인 check(`tools/node-pipeline/check.mjs`):**
  - 출처 분류(`cfg.allowSource`) → 허용 밖이면 `source` 실패, 교차 확인 안 되면 `communityUncorroborated` 실패.
  - 커뮤니티 출처는 가져오기 필수: `--no-probe`면 `communityUnprobed` 실패(베낌 검사를 건너뛸 수 없다).
  - **출처 글 베낌 검사:** 출처마다(공식·커뮤니티 모두) 가져온 글과 사실의 최장 공통 부분(공백 뺀 글자)을 재서 40자 이상 `copiedSourceHeavy` 실패, 25자 이상 `copiedSource` 확인. 기존 초안 페이지 베낌 검사(`copiedHeavy`·`copied`)와 같은 기준값(`COPY_FAIL`·`COPY_WARN`).
  - **두 출처 일치(휴리스틱):** 커뮤니티 노드에서 사실과 2그램 겹침이 0.5 이상인 출처 페이지가 2곳이 안 되면 `communityWeak` 확인(사람이 두 출처가 같은 사실인지 본다). 어긋남(충돌)은 자동으로 못 잡으므로 리뷰가 공식 우선으로 판정한다.
  - `sourceKind`는 LLM·사람이 아니라 파이프라인이 붙인다. 결과·리뷰 시트에는 출처별 숫자만(`sourceChecks`: URL·종류·최장 복사·겹침).
  - 금칙어 검사는 출처 종류와 무관하게 항상 돈다.
  - 식당 커뮤니티 후보는 `storeNameReview` 경고(특정 가게·브랜드 이름은 기계로 못 가려서 리뷰가 본다).
- **apply:** `sourceKind`를 노드에 남기고(키 순서 `sources` 뒤), 새 노드를 `checkNodeSources`로 다시 검사해 어기면 오류.
- 서버(`server/app`)는 노드 `sources`·`sourceKind`·`verifiedAt`를 시드(KG)에 넣지 않고(테스트로 확인) 출처 정책을 따로 강제하지 않는다. 그래프 파일이 테스트를 통과한 것만 배포되므로 충분하다.

## 하지 않은 것 / 나중
- 말풍선에 "커뮤니티 확인" 표시(근거 링크)는 이 작업 범위 밖. 필요하면 새 작업으로.
- 공식·커뮤니티 사실 충돌의 자동 판정(LLM 판정)은 하지 않았다. 리뷰 시트의 `communityWeak`·출처별 겹침 숫자를 보고 사람이(메인이) 판정한다.
- 정책 파일에 없는 사이트(네이버 블로그·뉴스·카페, 유튜브, 개별 언론사 누리집 등)는 받지 않는다(실패). 더하려면 이 ADR과 정책 파일을 함께 고친다(robots·약관 확인 표에 한 줄).

## 결과
- 메이플 노드 출처 상한이 공식 150~170개에서 풀리고, 식당은 장면 중심 노드(T-213)를 공공 자료 밖에서도 확인할 수 있다. 대신 커뮤니티 후보는 교차 확인·베낌 검사·금칙어 검사를 모두 통과해야 하고, 리뷰 시트에 출처 종류가 보인다.
- D-5의 "원문 저장·인덱싱 금지"는 바뀌지 않았다. 바뀐 것은 "노드 출처 URL에 커뮤니티를 적을 수 있다"와 그 조건이다.

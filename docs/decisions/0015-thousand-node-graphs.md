# 0015 관심사마다 노드 1,000개: 미리 계산 벡터, 반자동 후보, 묶음 회귀 기준

- 상태: 결정(미리 계산 벡터, 묶음 회귀 기준) + 제안(검색 변경, 반자동 후보 파이프라인은 T-194) — 2026-11-22, T-193
- 사용자 지시(2026-11-22): 관심사마다 노드 1,000개까지 **반드시** 늘리되, **정확도를 해치지 않는 선에서**. 한 문장에 맞는 비유는 여러 개일 수 있다("한 문장에 대해 비유가 다양하게 나올 수도 있잖아").

## 배경
지금 공통 그래프는 메이플 30노드, 식당 27노드다(다른 작업이 80/60까지 손으로 늘리는 중, T-194가 반자동 후보 파이프라인). 1,000개가 되면 세 가지가 깨진다.
1. **첫 로드.** 노드·태그 텍스트를 서비스 워커가 처음 볼 때 오프스크린에서 한 문장씩 임베딩한다(ADR 0011). 노드 텍스트(태그 설명·예문 + 이름·사실, ADR 0009)는 길어서 한 개에 0.6~1.2초 걸린다(호버 질의 0.12초와 다르다). 1,000개면 십수~수십 분이다.
2. **벡터 캐시.** `vecCache`(chrome.storage.local, T-110) 상한 2,000개는 두 관심사 × (노드 1,000 + 태그 21) = 2,042개를 못 담는다. 관심사를 바꾸면 LRU로 다른 관심사 벡터가 밀려나 다시 임베딩한다. 또 `saveVecCache`는 객체 통째로 쓴다.
3. **정확도.** 노드가 많아지면 지금 맞히는 문장의 1위를 비슷한 새 노드가 가져갈 수 있다. 여유(1·2위 점수 차)가 0.001~0.002인 가드 문장이 이미 있다(T-150·T-188).

## 결정 1: 미리 계산 벡터를 확장에 데이터로 동봉한다
- `npm run build:vectors`(`tools/build-vectors.mjs`)가 실제 확장(크롬, `admin.embedding` 모델 q8, 오프스크린 `embedEach` 한 문장씩, passage 접두어)으로 공통 그래프의 임베딩 항목 전부(`embedItems(mergeGraphs(공통), admin.retrieval)`, 확장과 같은 함수)를 임베딩해 `extension/data/vectors/<관심사>.json`에 쓴다. 데이터 파일일 뿐이라 원격 코드 금지(규칙 4)와 상관없다.
- **인코딩: float32 리틀엔디언 → base64**(`f32le-base64`, `lib/precomputed-vectors.js`). 런타임 벡터(`Float32Array.tolist()`)와 **비트 단위로 같다** → 점수·순위가 런타임과 같다. 768차원 한 개 4KB(base64), 1,000노드 관심사 하나에 약 4MB. float16(절반)·int8(1/4)은 크기는 작지만 점수가 1e-4 단위로 흔들려, 여유 0.001~0.002 문장의 1위를 바꿀 수 있어 채택하지 않았다. 확장 패키지(zip)는 어차피 압축된다.
- 파일 안에 `embedderId`·`passagePrefix`·`graphVersion`·`dim`이 있고, 키는 `sha1(텍스트)`(접두어 없이, `vecCache` 키와 같은 규칙). 관심사당 파일 하나(모델을 바꾸면 다시 만든다).
- **런타임 규칙**(`background.js` `ensureGraphVectors`): 오프스크린이 알려 준 `embedderId`와 `admin.embedding.passagePrefix`가 파일과 같고 해시가 있으면 그 벡터를 쓴다. 없는 텍스트(그래프를 고쳤는데 파일을 안 만든 노드, 로그인 오버레이, 교정 예문으로 바뀐 태그 텍스트)만 지금처럼 임베딩한다. 대체 임베더는 `embedderId`가 달라 파일을 쓰지 않는다(대체 경로 그대로). 미리 계산으로 덮인 텍스트는 `vecCache`에 넣지 않고, 예전 `vecCache`의 같은 키는 지운다. 결과·`embed:warmup`의 `vectorSources {precomputed, cached, embedded}`로 출처 수를 본다.
- **검증**: `npm run eval -- --precomputed`(그래프 벡터를 파일에서 꺼내 채점, 런타임과 비트 동일 수 출력). 2026-11-22: 메이플 49/49·식당 44/44 비트 동일, `--guard` 결과 그대로(메이플 평가셋 41/44·검증 13/14·회귀 없음, 식당 13/21·회귀 없음). `npm run build:vectors -- --verify`도 같은 비교를 한다.
- **CI 판정**(`npm run check:vectors`, `test` 잡): 못 쓰는 파일(형식, `embedderId`·접두어가 `admin.json`과 다름, 관심사 불일치)은 **실패**. 그래프와 어긋난 항목(빠짐·남음)은 **경고만**. 이유: 런타임은 어긋난 텍스트만 임베딩해 결과가 틀리지 않고, 다시 만들려면 실제 크롬 + 266MB 모델이 필요해 CI에서 강제할 수 없다. 그래프·태그 예문·`admin.retrieval` 텍스트 방식을 고친 PR은 `npm run build:vectors`로 다시 만들어 같은 PR에 커밋한다(`-- --strict`면 어긋남도 실패, 1,000개 묶음 PR에서 쓴다).

## 결정 2: 묶음 회귀 기준(1,000개까지 노드를 묶음으로 더할 때)
노드는 묶음(PR 하나, 예: 20~50개)으로 더한다. 묶음마다 아래를 **예외 없이** 지킨다. 합계가 올라도(순이익) 예외로 받지 않는다(사용자 지시 "정확도를 해치지 않는 선에서 반드시").
1. **진짜 1위 회귀 0.** 평가셋·검증셋·가드·식당 가드에서 맞던 문장의 1위가 바뀌면 둘로 나눈다.
   - **대안 정답(회귀 아님)**: 새 1위 노드가 ① 태그에 그 문장의 `expectTag`를 갖고 ② 그 노드 facts만으로 그 문장의 구조를 설명할 수 있고 ③ 메인이 한 줄씩 확인했다. 셋을 다 갖추면 그 노드를 그 문장의 `expectNodes`에 더하고(같은 PR, EVAL_LOG에 문장별로), 회귀로 세지 않는다.
   - **진짜 회귀**: 위 셋 중 하나라도 빠지면 회귀다. 특히 `expectTag`가 없는 노드가 1위를 가져가거나, 음성 문장(`forbidNodes`·비유 없어야 할 문장)에 노드가 붙으면 회귀다. `expectTag`가 없는 문장은 대안 정답으로 칠 수 없다.
   - 진짜 회귀가 하나라도 있으면 그 묶음은 받지 않는다(회귀를 만든 노드를 빼거나 고쳐 다시 잰다).
2. **여유 가드 악화 0.** `--guard --margin-guard`가 통과해야 한다. 아는 얇은 문장(`tools/eval-margin-known.json`, T-188)의 바닥은 래칫: 넓어지면 바닥을 올릴 수 있고(`--write-margin-known`), 더 얇아지는 것은 받지 않는다. 새로 얇아진 가드 문장도 받지 않는다.
3. 홀드아웃은 고르는 데 쓰지 않고 묶음마다 보고만 한다(맞던 홀드아웃 문장이 틀리면 EVAL_LOG에 적고 새 작업, 지금 원칙 그대로).
4. 묶음마다 `npm run build:vectors`로 벡터를 다시 만들고 `npm run check:vectors -- --strict` 통과.
5. 대체 임베더 기준선(T-179)은 지금처럼 `--baseline`으로 보고, 받아들이면 `--write-baseline`.

## 측정: 합성 1,000노드 (2026-11-22, 실제 확장 크롬, e5-base q8)
`node tools/scale-bench.mjs`(합성 그래프는 `.tmp/scale`에만, `data/common`에 넣지 않음) → `node tools/scale-analyze.mjs`(같은 실제 벡터로 크롬 없이 비교).
합성 노드 970·973개: 두 관심사의 진짜 사실 문장을 2~3개씩 섞고, 라벨은 진짜 노드 라벨 + "N호", 태그는 무작위 1~3개. **진짜 노드의 근접 중복**이라(가장 가까운 합성 노드 코사인 중앙 0.94, 진짜 노드끼리 최대 0.94) 실제로 들어올 그래프보다 훨씬 거친 비관적 스트레스다. 그래서 현실 쪽 신호로 "다른 관심사의 진짜 노드(검수된 서로 다른 개념)를 그대로 더하기"도 함께 쟀다.

- 근접 중복 노드가 있으면 지금 검색은 100개만 넘어도 무너진다. 무너지는 대부분은 같은 구조로의 이동이지만(합성 노드가 진짜 사실을 빌려 와서), 메이플 12·식당 6은 진짜 회귀다(사실은 빌렸는데 태그가 다른 노드).
- 진짜 노드 27개만 더해도 메이플 진짜 회귀 3·식당 1. 이 중 음성 "연말정산 때 세금 신고"는 **노드가 많아질수록 반드시 커지는 구조적 회귀**다: 약한 별칭 단서(T-149)의 `labelCueWords`가 공통 노드 **모든 라벨** 낱말을 단서로 쓴다. 식당 라벨 낱말 "신고"가 단서가 되어 약한 별칭 "세금"이 부스트됐다(메이플 그래프만이면 단서 없음, 확인함). 1,000개 라벨이면 일상 낱말 대부분이 단서가 된다.
- 두 단계 검색 후보(태그 관문 T=2·3·5, 직접 유사도 1단계 K=20·50)는 합성 1,000에서 진짜 회귀를 줄이지 못했다(메이플 14~15, 식당 4~6). 근접 중복은 어떤 관문도 통과하기 때문이다. 정확도는 검색 방식보다 **무엇을 그래프에 넣느냐**(중복·태그 정합)에 달려 있다.
- 여유: 합성이 들어가면 맞힌 문장 자체가 줄어 "얇은 여유 수"는 오히려 준다(10 → 2). 문장 수가 아니라 1위 변화 분류로 봐야 한다.

| | 미리 계산 없음 | 미리 계산 있음 |
| --- | --- | --- |
| 첫 로드(모델 캐시 있음, 1,021개 텍스트) | 메이플 **1,219초(20분)**, 식당 1,181초 | 메이플 **4.0초**(모델 로드 포함), 식당 전환 0.2초 |
| 관심사 되돌아가기 | 23초(상한 2,000에 밀린 21개 다시 임베딩) | 0.01초 |
| 호버(데모 제공자, 질의 임베딩 + 검색) 중앙 / p95 | 139 / 195ms | 138 / 169ms |

| 벡터 파일 | — | 관심사당 4.2MB, 해독 10~13ms |

- 노드 텍스트 한 개 임베딩이 약 1.2초(태그 설명·예문이 붙어 길다). 1,000노드에서 미리 계산 없이는 첫 호버가 20분 걸리므로 **미리 계산은 1,000개의 전제 조건**이다.
- `VEC_CACHE_MAX` 2,000은 미리 계산이 있으면 충분하다(공통 그래프 벡터는 vecCache에 들어가지 않고, 오버레이·바뀐 텍스트만 남는다). 미리 계산이 없으면 두 관심사 2,042개를 못 담지만, 그 경우는 파일이 낡은 묶음 PR 사이뿐이라 상한은 그대로 둔다(판정). `unlimitedStorage`는 이미 manifest에 있어 권한 변경은 필요 없다.
- 호버 시간은 1,000노드에서도 거의 그대로다(검색 계산 4ms). 성능 때문에 두 단계 검색이 필요하지는 않다.

## 제안(이 ADR에서 결정하지 않음, 정확도를 지키기 위해 1,000개 전에 필요한 것)
1. **약한 별칭 단서를 라벨 전체에서 떼기(필수, 별도 작업).** `labelCueWords`가 그래프가 커질수록 단서를 늘려 음성 문장을 깬다(위 측정). 단서 낱말을 그래프 파일의 명시 필드(예: 관심사 그래프 `cueWords`) 또는 별칭(`aliases`)만으로 좁힌다. 노드를 크게 늘리는 첫 묶음 전에 끝내야 한다. 음성 6문장이 회귀를 잡는다.
2. **근접 중복 관문(T-194 파이프라인 안).** 후보 노드 텍스트와 기존 노드의 코사인이 기존 노드끼리 최대값(메이플 0.94, 식당 0.95)을 넘으면 후보를 보류하고 사람에게 "기존 노드 X와 거의 같음"을 보여 준다. 코사인만으로는 구분이 약하므로(합성 최소 0.89 < 진짜 최대 0.94) 같은 사실 문장(정규화한 글자) 재사용도 막는다.
3. **태그 밀도 상한.** 한 태그를 가진 공통 노드 수에 상한(예: 관심사 노드의 10%)을 두고, 넘치면 묶음 PR에서 경고한다. 같은 구조 노드가 몰리면 대안 정답이 늘어 가드 문장의 기대 노드를 계속 고쳐야 하고, 다른 태그가 섞인 노드가 1위를 뺏기 쉬워진다.
4. **묶음 크기 20~50개 + 회귀 분류 자동 출력.** `scale-analyze`의 "같은 구조 / 다른 구조" 분류를 `npm run eval`에 붙여(기준 1위와 비교) 묶음 PR마다 진짜 회귀만 실패로 보이게 한다. 같은 구조는 메인이 사실을 확인하고 `expectNodes`에 더한다.
5. **두 단계 검색은 지금 도입하지 않는다.** 성능 이득이 필요 없고(4ms), 측정한 관문 변형은 정확도를 지키지 못했다. 1,000개가 되면 다시 잰다.
6. **vecCache 저장 형식**(작은 개선): 숫자 JSON 대신 같은 f32 base64로 저장하면 1/4로 줄고 저장 549ms가 줄어든다. 미리 계산이 있으면 급하지 않다.

## 반자동 후보 파이프라인(T-194)
T-194는 출처(공식 공지·사전)에서 노드 후보를 초안으로 만들고(LLM), 검증(`validateGraph`, 규칙 2 수치 금지, 규칙 11 금칙어)과 사람 검수를 거쳐 묶음 PR로 넣는 도구다. 이 ADR은 그 묶음이 지켜야 할 기준(결정 2)과 벡터 재생성(결정 1)을 정한다. 파이프라인 안에서 미리 걸러야 할 것은 제안 절의 근접 중복 관문이다.

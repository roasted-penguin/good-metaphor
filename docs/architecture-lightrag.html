LightRAG 아키텍처

EC2 한 대에 LightRAG를 라이브러리로 감싼 analogy-api를 두고, 엔티티·관계 추출만 Tailscale로 내 M2 맥의 Ollama에 맡겨요. 호버 경로에는 맥이 없어서 맥이 꺼져 있어도 비유는 나와요. PoC 월 비용은 약 $31이에요.

질의 흐름

호버 한 번은 LLM 2회와 검색 1회

키워드 추출은 우리가 대신하고, 검색은 LightRAG에, 답변 생성은 다시 우리 프롬프트에 맡겨요. 그래야 추상 태그 통제와 근거 검증을 유지할 수 있어요.

호버 한 번의 순서

주황 = LightRAG 기본 동작 대신 우리가 쥐는 단계 · 시간은 측정 전 예상치
  1. 확장 → POST /v1/analogy문장, 커서 단어, 앞 문장, 설치 토큰(로그인 시 JWT). 서버는 먼저 결과 캐시(문장 해시 + 워크스페이스 버전)를 봐요.
  2. 키워드 (Gemini Flash-Lite)한 번의 호출로 ll_keywords(구체 개념)와 hl_keywords(추상 구조)를 뽑아요. hl_keywords는 통제 어휘 18개 중에서만 고르고, 맞는 게 없으면 빈 배열이에요.
  3. 검색 (LightRAG)QueryParam(mode="hybrid", hl_keywords, ll_keywords, only_need_context=True)로 공통·내 워크스페이스를 동시에 검색해요. 키워드를 직접 넘기므로 LightRAG는 키워드 LLM을 부르지 않고 컨텍스트만 돌려줘요.
  4. 병합내 워크스페이스 결과를 앞에 두고 후보 3개를 골라요. 오버레이 설정(숨김, 가중치, useCommon)을 여기서 적용해요.
  5. 비유 (Gemini Flash)기존 buildAnalogyPrompt와 같은 규칙으로 한 번 호출해요.
  6. 근거 검증 → 응답nodeId가 후보에 없으면 비유를 숨겨요. 응답은 기존 확장의 결과 형식 그대로라 말풍선 코드는 바뀌지 않아요.

통제 어휘가 핵심이에요. 금융 문장의 키워드 LLM과 메이플 문서의 추출 LLM이 같은 목록에서 고르므로 "기간당 한도" 같은 키워드가 양쪽에서 글자 그대로 만나요. 자유 키워드에 맡기면 한쪽은 "API 요청 제한", 다른 쪽은 "결정석 판매 상한"이라 서로 못 만나요.

IFBench는 Artificial Analysis 값(API, 풀 정밀도)이라 로컬 Q4는 이보다 낮아요. thinking은 청크 20개로 네 조합(모델 2 × 켬/끔)을 돌려 파싱 실패율, 트리플 수, 추상구조 연결 수, 청크당 시간을 비교해 정해요. LightRAG의 JSON 출력 모드를 켜면 형식 위반이 줄어 thinking을 꺼도 될 수 있어요.

# Ollama는 로컬에만 열고, Tailscale이 테일넷에만 노출한다
launchctl setenv OLLAMA_HOST 127.0.0.1:11434
launchctl setenv OLLAMA_NUM_PARALLEL 1      # 동시 요청 1개
launchctl setenv OLLAMA_KEEP_ALIVE 5m       # 끝나면 5분 뒤 메모리에서 내림
launchctl setenv OLLAMA_CONTEXT_LENGTH 16384
ollama pull gemma4:12b
tailscale serve --bg --tcp 11434 tcp://127.0.0.1:11434
시간창launchd가 점심(12:10~13:00)과 밤(23:00~07:00)에만 Ollama를 켜고 caffeinate -i. 바로 노트북을 써야 하면 Ollama만 끄면 돼요.
처리량 (예상)청크당 1~2분, 청크 100개에 2~3시간. M2 Pro 칩(메모리 16GB)으로 확인돼서 M2보다 메모리 대역폭이 두 배예요. 첫 실험에서 실측해요.

리스크

가장 큰 위험은 작은 모델의 추출 품질

LightRAG 권장은 32B 이상인데 16GB 맥에서는 12B가 한계예요. 그래서 시드 그래프와 통제 어휘로 뼈대를 고정하고, 모델은 그 사이를 채우는 역할만 맡겨요.

`CLAUDE.md`의 "지켜야 할 규칙"과 "작업 방식", 그리고 `docs/TASKS.md`를 읽고 아래 순서로 진행해.
superpowers 스킬을 단계마다 부른다. 스킬이 없으면 각 단계에 적힌 내용을 직접 따른다.
superpowers 스킬과 이 문서가 다르면 이 문서와 CLAUDE.md가 우선이다(브랜치·PR·기록 방식 등).

## 1. 준비 · 작업 고르기 · 브랜치
`/next-task`의 1~3단계를 그대로 따른다. 인자: $ARGUMENTS
- 브랜치는 `task/<ID>-<짧은-영문-슬러그>`이고 `origin/dev`에서 만든다. `using-git-worktrees`는 쓰지 않는다.
- 작업 상태를 `진행`으로 바꾸는 커밋까지 한다.

## 2. 요구 정리 (`superpowers:brainstorming`)
- TASKS.md의 해당 작업에서 "할 일"과 "완료 기준"을 그대로 인용한다.
- 관련 코드와 테스트를 읽고, 완료 기준이 모호하거나 서로 부딪치는 곳만 질문한다. 질문은 한 번에 하나씩 한다.
- 설계 문서는 따로 만들지 않는다. 설계가 바뀌면 `docs/decisions/`에 ADR을 쓴다(구현 단계에서).

## 3. 테스트 계획 (`superpowers:writing-plans`)
계획은 대화에 보여 주고 `.tmp/test-plan-<ID>.md`에 저장한다. `docs/superpowers/` 같은 새 폴더는 만들지 않는다.

**완료 기준 ↔ 테스트**

| 완료 기준 | 테스트 파일 | 종류 | 입력·상황 | 기대 결과 | 지금 실패하는 이유 |
| --- | --- | --- | --- | --- | --- |

- 종류: 순수 로직은 `tests/unit`(node:test), 확장 동작은 `tests/e2e`(Playwright, 가짜 LLM :8765).
- 완료 기준마다 테스트가 최소 하나 있어야 한다. 자동으로 못 보는 것(실제 키 스모크, `npm run eval` 수치, 실제 크롬 체감 속도)은 "수동 확인" 줄로 따로 적고 확인 방법을 쓴다.
- 지켜야 할 규칙(근거 밖 비유 숨김 등)을 건드리는 작업이면 그 규칙이 깨지지 않는지 보는 테스트도 넣는다.

**구현 순서** 테스트 한 묶음씩 3~7단계로 적는다. 단계마다 고칠 파일을 쓴다.

## 4. 확인받기 (여기서 멈춤)
- 계획을 보여 주고 **사용자가 명시적으로 승인할 때까지 기다린다.** 승인 전에는 테스트·코드를 쓰지 않는다.
- 고치라는 말이 있으면 계획을 고쳐 다시 보여 준다.

## 5. 구현 (`superpowers:test-driven-development`)
구현 순서의 단계마다 다음을 반복한다.
1. 계획의 테스트를 쓴다.
2. 돌려서 **계획에 적은 이유로 실패하는지** 확인한다. 바로 통과하면 테스트가 잘못된 것이니 고친다.
3. 통과할 만큼만 구현한다. `src/offscreen-src.js`를 고쳤으면 `npm run build`.
4. 다시 돌려 통과를 확인하고 커밋한다: `test(<ID>): ...` → `feat(<ID>): ...` / `fix(<ID>): ...`.

- 통과시키려고 테스트를 약하게 고치지 않는다. 계획을 바꿔야 하면 멈추고 무엇을 왜 바꾸는지 사용자에게 말한다.
- 테스트가 예상과 다르게 실패하면 `superpowers:systematic-debugging`으로 원인부터 찾는다.

## 6. 전체 확인 (`superpowers:verification-before-completion`)
- `npm test`(단위 + e2e)를 돌리고 통과한 개수를 출력 그대로 확인한다. 돌리지 않았거나 실패했으면 "완료"라고 말하지 않는다.
- 검색·생성에 영향이 있으면 `npm run eval`(모델을 못 받으면 `npm run eval:fallback`이라고 명시) 후 `docs/EVAL_LOG.md`에 한 줄.
- 계획의 "수동 확인" 줄은 할 수 있으면 하고, 못 했으면 못 했다고 남긴다.

## 7. 기록 · 올리기
- `docs/TASKS.md`: 상태를 `리뷰`로 바꾸고 작업 로그에 한 줄. 새로 발견한 문제는 새 T-번호로 추가.
- `/ship` 절차를 따른다. PR 본문의 "테스트 계획" 칸에는 3단계 표를 옮기고, 실제로 통과한 줄만 체크한다.

마지막에 PR 링크, 추가한 테스트 수, 확인하지 못한 것을 3줄 이내로 알려 줘.
